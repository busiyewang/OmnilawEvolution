# Hermes 技能进化：设计方案（待确认）

状态：**提案**，2026-10-26。未实现，未产生任何费用。下面的费用都是估算，第 6 节的试跑用来实测。

## 1. 目标与范围

把 Hermes 的**技能文件**（`SKILL.md` 及附属文件）作为第二个进化对象。改动要像 `collector/dedup.py` 一样，
经过“提案 → 候选 → 评测 → 人工确认 → 发布 / 回滚”的流程才能生效。

| 对象 | 是否纳入 | 理由 |
|---|---|---|
| 技能（`agent/<identity>/skills/`） | **纳入** | 文本形式、体积小、对行为影响大；改动可以 diff 和回滚；Hermes 本身有暂存审批机制 |
| Hermes 源码（`_vendor/hermes-core.tar.gz`） | 不纳入 | 几十万行，评测不可行；sha256 校验保持不变，只能由人工重新打包升级 |
| 记忆（`memories/`） | 默认不纳入 | 记的是用户偏好和环境事实，无法用任务成功率评测；改为写入定期记录，供人审查（见 §8 决策 3） |
| `SOUL.md`、系统提示、工具描述 | 第一版不纳入 | 影响所有任务，需要更大的评测集；等技能进化跑稳后再考虑 |

## 2. 现状（已核对源码）

* Hermes 的 `skill_manage` 工具，以及每轮对话后的后台复盘（`agent/background_review`），都会**直接**写入技能目录。
  目前没有评测，也不需要人确认。
* Hermes 原生支持 `skills.write_approval: true`（`tools/write_approval.py`）。打开后，所有技能写入都不落盘，
  而是暂存到 `<HERMES_HOME>/pending/skills/<id>.json`，内容是完整的调用参数，可用 `apply_skill_pending` 重放，
  也可用 `skill_pending_diff` 生成 diff。**因此不需要修改 Hermes 源码。**
* Hermes 自带 `skill_usage.py`（各技能的使用次数）和 `skill_ledger.py`（每次改动前后的快照）。
  可以用来挑选值得优化的技能，并核对实际改动。
* Omnilaw 每个会话有自己的 `HERMES_HOME`（`agent/<identity>/sessions/<id>`），技能目录通过符号链接在会话间共享。
  所以暂存文件分散在各个会话目录下，需要统一收集。

## 3. 总体流程

```
候选来源                          评测                                  发布
──────────                        ──────                                ──────
① Hermes 暂存的技能写入  ─┐
② 评测失败 → 研究 → 提案 ─┼→ skill 候选 → 开发集（配对）→ 保留集（配对）→ READY → 人工确认 → 写入技能目录（Git）
③ 用户反馈 / 人工提交     ─┘          （沙箱内跑 Hermes）                          ↘ 不达标：REJECTED，保留记录
```

沿用现有的状态机、`runs` / `evaluations` 表、每日预算、确认码和定期记录。新增的是候选的种类（`kind=skill`）
和一个智能体任务评测器。

## 4. 组件

### 4.1 技能仓库（受控）

* 技能目录改为一个**独立的 Git 仓库**（`.omnilaw/state/agent/<identity>/skills/.git`）。每次发布一个提交，回滚等于 `git revert`。
* 会话配置写入 `skills.write_approval: true`，同时打开后台复盘，让 Hermes 继续提出改进，但只能暂存。
* 新增 `skill_collect` 任务：收集所有会话下的 `pending/skills/*.json`，去重后建成候选（`origin=hermes`），
  收集后删除源文件。暂存内容是外部文本，只当数据处理，不会执行。
* 随包技能（59 个）作为初始版本提交，记为 `seed`。

### 4.2 智能体任务评测集（`eval/agent_tasks/`，受保护）

每个任务一个目录：

```
eval/agent_tasks/<split>/<task-id>/
  task.json      # 指令、类别、相关技能、最大轮数 / 秒数、所需工具
  workspace/     # 初始文件（小型仓库、数据文件等），每次运行都复制一份全新的
  check.py       # 确定性判定：退出码 0 = 成功；只读 workspace，不调用模型
```

* 只用**可以确定性判定**的任务：修 bug 让测试通过、按规格生成文件、数据清洗后与期望值比对、
  在本仓库中定位并回答可核对的问题等。第一版不用模型打分。
* 第一版**不包含网页和浏览器任务**：结果依赖外部网站，无法复现，而且评测沙箱禁网。
* 规模：开发集 16 个、保留集 16 个，每个任务标注类别（编码 / 调试 / 文件与数据 / 本仓库操作）。
  另有 6 个“守卫任务”，与候选技能无关，用来检查新技能是否干扰其他任务（技能索引对所有任务可见）。
* 任务由我起草，**由你审核确认**后才冻结（见 §8 决策 1），冻结后记录评测器版本和哈希。候选不能读写 `eval/`。

### 4.3 评测运行器（`agent_eval.py`）

* 每次运行在一个新的临时目录中进行：复制 workspace，并准备一个临时 `HERMES_HOME`，
  其技能目录是**候选版本的技能快照**（基线运行用当前版本）。记忆为空，会话库为空，避免历史信息干扰。
* 进程放在 `sandbox-exec` 中：只能写临时目录；网络只开放 `127.0.0.1` 上的 AgentBridge 端口；
  不能读 `eval/`、凭据文件和真实的技能目录。
* 模型请求全部经过 AgentBridge，与研究和聊天共用同一个每日费用账本。
  另设一个子上限 `skill_eval.max_daily_cost_usd`，保证评测不会吃光聊天的额度。
* 评测时关闭后台复盘和技能写入（`skip_background_review`，技能目录只读），评测过程本身不能修改技能。
* 每次运行记录：是否成功、轮数、耗时、输入和输出 token、费用、使用了哪些技能（取自 `skill_usage`）。

### 4.4 采用规则（预先确定，不为某个候选临时改动）

智能体运行不确定，同一任务每次结果可能不同，所以采用**配对比较 + 重复运行**：

1. **开发集筛选**：只跑与候选相关的类别。每个任务基线和候选各跑 2 次。
   候选成功次数 ≥ 基线才进入保留集；否则 REJECTED，并写明原因。
2. **保留集决定**：相关类别的保留任务加 6 个守卫任务，每个任务基线和候选各跑 3 次。要求同时满足：
   * 相关任务成功次数比基线**多至少 2 次**（例如 8 个任务 × 3 次 = 24 次中，从 15 次提高到 17 次以上）；
   * 守卫任务成功次数**不少于基线**；
   * 每个成功任务的平均费用不超过基线的 1.3 倍。
3. 保留集的曝光次数受每日上限限制（沿用 `max_holdout_evals_per_day`），防止反复试探保留集。
4. 达标后状态为 READY；**发布仍需你用确认码确认**。发布后进入观察期：
   一周内真实会话中这个技能相关任务的失败若被你标记，可以一键回滚。

这套规则样本小，只能识别比较明显的改进，小幅提升会被判为“未达标”。这是有意为之：宁可漏掉，也不误采用。

### 4.5 候选生成

* ① **Hermes 暂存**：直接把暂存的写入作为候选，不额外花钱。
* ② **失败驱动**：开发集中失败的任务（包含轨迹摘要：最后的报错、调用了哪些工具）交给规划器。
  规划器用 DeepSeek 生成技能补丁，补丁只能修改 `skills/`，并通过 Hermes 自带的技能检查（`skill_linter`）。
  轨迹中的外部文本只当数据。
* ③ **人工**：你在聊天里说“把 xx 的经验写成技能”，同样只生成候选，不直接写入。
* 每个候选必须写明假设：改了什么，预计会改善哪一类任务。

### 4.6 记录与可见性

* 日报和周报增加“技能”一节：新候选、评测结果（成功次数对比、费用）、发布和回滚的 diff。
  如果你选择记忆不纳入评测，这一节也列出记忆的增删。
* `CHANGELOG.md` 增加技能版本记录；`KNOWLEDGE_BASE.md` 不变。
* 聊天命令：`技能 候选`、`技能 评测 <id>`、`采用 <id>`、`回滚 技能 <版本>`。

## 5. 费用估算

价格按本机配置：DeepSeek Flash 输入 $0.3 / 百万 token，输出 $1.2 / 百万 token（未计缓存折扣，偏保守）。

| 项 | 估算 | 依据 |
|---|---|---|
| 单次任务运行 | **约 $0.05–0.20**，中位约 $0.10 | 约 10–20 次模型调用；Hermes 系统提示加工具定义约 1–2 万 token，上下文随轮次增长，平均每次约 2 万输入、500 输出 |
| 开发集筛选（1 个候选，相关类别约 6 个任务） | 6 × 2 次 × 2 组 = 24 次 ≈ **$2.4** | 基线运行结果可以复用 7 天，复用后约 $1.2 |
| 保留集（相关约 8 个任务 + 6 个守卫） | 14 × 3 次 × 2 组 = 84 次 ≈ **$8.4** | 复用基线后约 $4.2；只有通过开发集的候选才会跑 |
| 每个候选合计 | 未通过开发集：约 $1–2.5；跑完全程：约 $5–11 | |
| 试跑实测（§6） | **约 $1–2** | 4 个任务各跑 2–3 次 |

和预算的关系：

* 本机每日上限是 $5，聊天也要用。建议给技能评测单独设 **$2/天**的子上限。
  这样一个候选从开发集到保留集大约需要 2–5 天，期间进度会出现在日报里。
* 现有费用守卫在每次调用前按完整上下文容量（1,048,576 token）加最大输出**预扣**约 $0.32，返回后再按实际结算。
  所以评测只能串行运行，不能多个任务并发，否则预扣额会先撞到上限。
* 实际成本以试跑测量为准。如果单次运行明显超过 $0.20，我会先回来找你调整任务规模，再继续。

## 7. 风险与限制

* **样本小、噪声大**：只能识别明显的改进，见 §4.4。
* **评测集的代表性**：任务如果和你实际的使用方式差距很大，“评测里变好了”不代表实际变好了。
  所以任务要由你审核，后续可以从真实会话中挑选失败案例，加进新版本的评测集。
* **评测环境与真实环境不同**：评测在沙箱中运行，禁网，记忆为空；真实会话有网络、有记忆、有完整权限。
* **Hermes 升级**：重新打包 Hermes 后，技能格式或工具行为可能变化，需要重新跑基线。
* **暂存文件的安全**：暂存的技能写入可能受网页等外部内容影响（提示注入）。
  这些内容只作为候选文本，必须通过评测和你的确认才能生效，评测环境也是禁网的沙箱。
* **只在 DeepSeek 环境可用**：Hermes 需要 Python 3.14，并且 `model.provider=deepseek`。
  这个仓库目录下的 `omnilaw.json` 目前仍是 mock，`.venv` 是 Python 3.13，所以真实试跑要在你已经配好 DeepSeek 的环境里进行。
